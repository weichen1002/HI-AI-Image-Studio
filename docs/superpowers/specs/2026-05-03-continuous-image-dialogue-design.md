# 连续对话生图升级设计

## 目标

让当前“对话创作”模式更接近 OpenAI 官方 ChatGPT 的连续修图体验：

- 优先复用上游支持的原生响应链能力
- 上游不支持时，自动降级为“上一张结果图继续编辑”
- 保持现有前端交互基本不变
- 避免因为兼容网关能力不足导致整条链无法继续

## 现状问题

当前实现会把历史 prompt、输入图和部分 `outputItems` 手动重放给 `/responses`，但没有真正把 `previous_response_id` 作为续链参数传回上游。这使得当前模式更像“带上下文重新生成”，而不是“基于上一轮结果继续编辑”。

主要表现为：

- 连续性弱，模型更容易偏离上一张图
- 局部修改不稳定，角色和构图容易漂移
- 兼容网关不完整支持时，体验与官方差距明显

## 方案概览

采用“能力探测 + 分层降级”的设计：

1. 优先检测上游是否支持原生响应链续写
2. 如果支持，则使用 `previous_response_id` 或等价参数进行连续编辑
3. 如果不支持，则回退到“上一轮结果图作为下一轮输入图”的图片接力模式
4. 前端展示当前链路使用的是哪种连续模式，避免误解

## 服务端设计

### 1. 能力探测

在 `HiapiService` 增加网关能力判断，至少区分两类能力：

- `response_chain_supported`
- `image_replay_supported`

第一阶段以静态配置和请求试探结合实现：

- 默认认为兼容网关“不保证支持”原生续链
- 当用户首次进入连续创作时，优先按原生续链发送
- 若上游返回参数不支持、字段缺失或明显不兼容，则将当前链标记为图片接力模式

### 2. 原生续链模式

当上游支持时：

- 每轮请求只携带当前用户要求
- 携带上一轮 `responseId` 作为续链依据
- 不再手工重放整段 `historyTurns`

这样可以最大限度贴近官方产品的连续编辑体验。

### 3. 图片接力降级模式

当上游不支持原生续链时：

- 取上一轮结果图的本地 URL
- 转为输入图传给模型
- 当前轮仅附带必要文字说明
- 仅保留少量最近历史作为辅助，不再依赖整段 `outputItems`

该模式不是真正的官方响应链，但会比当前“纯重放历史”更稳定。

### 4. 数据模型调整

保留现有字段：

- `responseId`
- `previousResponseId`
- `continuationChainId`

新增字段建议：

- `continuationStrategy`
  - `response_chain`
  - `image_replay`
- `lastResultImageUrl`

用于明确每轮到底走的是哪种连续策略，便于调试、降级和后续迁移。

## 前端设计

前端仍保留当前“对话创作”入口，但增加一条轻提示：

- `当前模式：原生续链`
- `当前模式：图片接力`

这样用户能理解为什么某些链路更像官方，而某些链路只是尽量模拟。

无需新增复杂操作。用户仍然只需要：

- 选择基底图或最近结果
- 输入这一轮修改要求
- 提交继续创作

## 错误处理

需要重点处理以下情况：

- 上游不识别 `previous_response_id`
- 上游返回了 `responseId`，但下一轮不能复用
- 原生续链失败，但图片接力仍可继续
- 图片接力模式下参考图丢失或本地文件不存在

处理原则：

- 原生续链失败时，自动回退到图片接力
- 回退成功后，不让整次请求失败
- 仅在两种模式都失败时，才向前端返回错误

## 测试与验证

至少验证以下场景：

1. 上游支持原生续链时，连续两轮修改保持主体连续
2. 原生续链失败时，自动回退为图片接力仍能成功
3. 历史记录中的连续链能正确显示当前策略
4. 删除历史记录时，结果图与接力所需本地文件清理正常

## 结论

本次升级不追求一次性完全复制官方 ChatGPT 的内部能力，而是优先把现有实现从“重放历史再生成”升级为：

- 能用原生续链时，真正续链
- 不能用时，稳定退化到图片接力

这是当前兼容网关场景下，最稳妥且最接近官方体验的实现路径。
